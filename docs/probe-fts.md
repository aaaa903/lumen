# FTS5 trigram 原型结论

M0 的第一件事（PRD §11 风险 1）：确认中文全文搜索能不能直接落在 SQLite 的 FTS5 上。

- 测量时间：2026-10-21
- 运行时：Electron 44.9.3 / Node 24.22.0 / SQLite 3.53.4（`node:sqlite`）
- 复现：`npm run probe:fts`，原始数据在 `docs/probe-fts.json`

## 语料

500,310 字，拆成 459 个章节块，覆盖 5 本书。语料由 12 个固定句子轮转拼接而成，**重复度远高于真实书籍**，因此下面的索引体积是乐观值。

## 结果

| 项目 | 普通表 | trigram 表 |
| --- | --- | --- |
| 数据库体积 | 1.80 MB | 2.65 MB（1.47 倍） |
| 50 万字一次性写入 | 6.8 ms | 35.6 ms |

| 查询 | MATCH（ms / 命中） | LIKE（ms / 命中） |
| --- | --- | --- |
| 中文 2 字：灯光 | 0 / 0 | 0.45 / 153 |
| 中文 2 字：书店 | — | 0.64 / 0 |
| 中文 3 字：旧车票 | 0.02 / 153 | 0.45 / 153 |
| 中文 4 字：木地板 | 0.02 / 153 | 0.43 / 153 |
| 中文 6 字：玻璃上缓慢 | 0.07 / 153 | 0.43 / 153 |
| 英文单词：library | 0.11 / 153 | 0.46 / 153 |
| 不存在的词：鲸鱼骨 | 0.01 / 0 | 0.62 / 0 |
| 对照组：无索引表的 LIKE | — | 0.51 / 153 |

排序（`bm25`）与片段（`snippet`）均正常：一次排序查询 0.2 ms，片段带 `<mark>` 标记。

## 结论

1. **trigram 可用。** FTS5 在 `node:sqlite` 里编译进运行时，`tokenize='trigram'` 创建成功，中英文子串都能命中，`snippet` 与 `bm25` 行为符合预期。
2. **两字查询必须走 LIKE。** trigram 要求查询至少 3 个字符，`MATCH '灯光'` 返回 0 行而不是报错，容易被误判成「没有结果」。搜索层按长度分流：≥3 字用 `MATCH`，<3 字用 `LIKE '%…%'`。
3. **两字查询不必另建索引。** 50 万字库上 `LIKE` 耗时 0.45–0.64 ms，与 trigram 的差距只有零点几毫秒；即使书库涨到 500 万字，按线性估算也在 10 ms 量级，远低于 PRD 的 200 ms 预算。MVP 不做二元组倒排。
4. **索引体积可接受。** 语料高度重复时只有 1.47 倍；真实书籍估算 2–3 倍，仍低于 PRD 设定的 1.5 倍「索引与标注合计」上限的风险线——这一条需要在 M3 用真实书复核，若超过 3 倍再考虑只索引标注所在章节或压缩正文。
5. **写入成本一次性。** 50 万字建索引约 36 ms，可以放在打开书籍后的空闲时机，不需要进度条。

## 对实现的影响

- 搜索语句统一由 `shared/search-query.ts` 构造，禁止在别处拼 `MATCH` 字符串；查询串先去掉 `"` 再整体包引号，避免 FTS 语法注入。
- 短查询分支要显式标注原因，避免后来者「统一改成 MATCH」。
- M3 验收时补一组真实书籍（≥3 本、不同排版）的体积与耗时数据，追加到本文。
